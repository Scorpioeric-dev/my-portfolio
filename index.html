Forge: multi-agent AI software delivery pipeline

Operational

Four AI roles turn a plain-language request into planned, coded, tested, and committed software, with a human holding the scope.

  • Python
  • Local LLMs (Ollama)
  • State machines
  • pytest
  • JSON schema
The problem
Autonomous coding agents tend to drift. They quietly redefine scope, grade their own work generously, and cost money on every token.
What I built
  • A Planner, Coder, Tester, and Shipper, each bound by a fixed contract so no agent can silently change another's job.
  • A Python state machine that retries implementation bugs within a capped budget but halts the whole pipeline on any specification change until a human approves.
  • Append-only audit logging of every phase transition, with state saved to disk so a halted run resumes exactly where it stopped, even days later in a new process.
Design choices
  • Moved inference to fully local models, removing per-token cost and API governance friction.
  • Added automated JSON repair and schema normalization to handle malformed model output.
  • The test step runs real pytest suites instead of trusting the model's self-assessment. I also found and fixed a defect where empty acceptance criteria passed automatically.
Where it's used
It built the production code for other automations in this section, including an enterprise data write-back integration.

Governed CRM write-back automation

Built and tested, rollout staged

Automated bulk updates to an enterprise CRM where direct API access is deliberately blocked, using the sanctioned channel instead of a workaround.

  • Python
  • SQL
  • Cloud data warehouse
  • Headless bulk-load CLI
  • YAML config
  • pytest
The problem
A recurring manual review-and-update workflow, in an organization where API access was blocked on purpose. Browser automation or third-party connectors would have worked, and would have been the wrong call.
What I built
  • A warehouse query that detects records meeting business trigger conditions and reads current state, so corrected records never fire twice.
  • SOP-compliant classification tagging, a formatted CSV, and a headless run of the organization's approved bulk-load tool, keyed on record ID so duplicates cannot be created.
Design choices
  • Every run parses the tool's success and error output, reports each failed row with its cause, and exits non-zero, so partial failures cannot pass silently between scheduled runs.
  • Sandbox-first rollout, a dedicated integration user for headless runs under single sign-on, and credentials kept out of code.
  • Automated tests with all external systems mocked.

AI vision quality review for field installations

In design

AI pre-screening of technician photos and responses against written quality standards, with a human approving every verdict until the accuracy record justifies more.

  • Vision LLMs
  • Evaluation design
  • Human-in-the-loop
  • Python
The problem
Each installation work order includes required questions and photo evidence, and a quality representative reviews them by hand. That review sits between field submission and sign-off, and consistency depends on who does it.
Work so far
  • Mapped where responses and photos land in the data platform.
  • Turned written quality standards into criteria a model can evaluate.
  • Assembled graded historical reviews as validation ground truth.
  • Evaluating hosted and local vision models against the organization's API governance constraints.
Design choices
Staged autonomy. The AI flags issues and a human approves every order first. Clear passes graduate to auto-approval only after a measured accuracy track record, and every verdict traces to a written criterion.

Autonomous customer activation outreach

In production

A daily pipeline that finds customers whose installed equipment is ready to switch on, fixes blocking data issues, and emails each one how to finish.

  • Python
  • SQL
  • Selenium (headless)
  • HTML email (SMTP)
  • Scheduled jobs
The problem
Daily manual lookups and one-by-one emails to customers who were approved to activate but hadn't yet.
What I built
  • Three stages: a detection query, automated headless-browser remediation of upstream equipment-portal data issues (disabled settings, incorrect flags, missing dates), then a personalized how-to email.
  • Email templates chosen by equipment manufacturer, with photos of the customer's actual hardware.
  • It handles dozens of customers every day without anyone touching it.
Reliability
  • An independent watchdog job verifies the daily audit report was freshly written and alerts if customer emails failed. The system monitors itself.
  • A portal failure never blocks customer outreach, every external connection has a hard timeout, and failures capture a screenshot and page source for debugging.
  • Each run emails the team a per-customer record of actions taken and email status.

Sentinel: cadence compliance and missed follow-up detection

In production, read-only

Turns a team's outreach rules into a tested detection engine that flags missed follow-ups the same day.

  • Python
  • SQL
  • Rules engine
  • pytest
The problem
Missed customer follow-ups surfaced only when someone happened to audit by hand.
What I built
  • The team's escalation clocks, stage conventions, and handoff templates, encoded as deterministic rules and documented in a single source-of-truth file.
  • A manager digest plus a personalized daily worklist for each specialist, with flag history across thousands of records so trends are visible.
Design choices
  • Detection logic is separate from input and output ("rows in, classified rows out"), so the rules are tested in isolation.
  • I piloted it on myself first and fixed silent scheduled-run failures before the team saw anything.
  • Read-only by design. It never writes back to the system of record.

Portal access compliance audit

In production

A weekly audit that verifies build partners hold the required portal access across hundreds of systems.

  • Python
  • Selenium
  • SQL
  • Scheduled reporting
The problem
Checking access system by system is impractical at this volume, so missing access showed up only when it blocked field work.
What I built
A weekly scheduled run that checks every system against contract data and emails an actionable CSV to the team.
Design choices
Guards against false negatives. A failed login aborts the run instead of continuing unauthenticated, and session-drop redirects are classified as errors rather than misreported as missing access.

Automated case creation and workload balancing

In production

Each morning, finds work that needs an on-site visit and distributes it evenly across the operations team.

  • Python
  • SQL
  • Round-robin assignment
  • CRM import automation
The problem
Operations staff triaged and assigned on-site casework by hand every morning.
What I built
A weekday job that identifies qualifying projects across three business segments, assigns them round-robin so workload stays even by construction, and emits a CRM-import-ready file.
Ownership
I took it over from the operations manager and documented known risks and open items in a handoff-quality README, so it runs as a maintained product rather than a script.
